# TopoScope

TopoScope is a graph-scoped LLM agent for PCB schematic design. It generates PCB netlists from natural-language design requirements under real IC pin constraints, topology-guided context scoping, and graph-based electrical rule verification.

The repository includes the generation agent, benchmark cases, component data, prompts, evaluation scripts, assertion-based functional verification, and experiment runners for baseline, ablation, and full-system settings.

## Directory Overview

### Root files

- `agent.py`  
  Main implementation of the TopoScope generation agent.

- `requirements.txt`  
  Python dependencies required by the project.

### `ERC_rules/`

Contains rule definitions and enumerations for electrical rule checking.

- `rule_enums.txt`  
  ERC rule enumeration file.

### `benchmark/`

Contains benchmark cases, component data, experiment runners, evaluation scripts, results, and reports.

#### `benchmark/cases/`

- `benchmark_cases.json`  
  Natural-language benchmark task descriptions and metadata.

#### `benchmark/component_data/`

- `Extracted_Components.json`  
  Structured component knowledge base extracted from datasheets, including pins, electrical types, reference circuits, and ERC-related information.

#### `benchmark/configs/`

- `llm_clients.json`  
  LLM provider configuration file. This file defines provider names, model names, API base URLs, and environment variable names for API keys.

#### `benchmark/eval/`

Evaluation utilities for generated connection sets and experiment outputs.

- `assertion_checker.py`  
  Checks functional assertions against generated netlists.

- `connection_metrics.py`  
  Computes connection-level metrics such as connection recall and precision.

- `erc_checker.py`  
  Runs ERC-style verification over generated designs.

- `evaluate.py`  
  Main evaluation entry point.

- `export_tables.py`  
  Exports aggregated experiment results into table-ready formats.

- `graph_utils.py`  
  Utility functions for graph construction, traversal, and conversion.

- `hallucination_report.py`  
  Generates hallucination-related diagnostic reports.

- `pass_checker.py`  
  Computes pass/fail outcomes according to benchmark criteria.

- `pin_normalizer.py`  
  Normalizes pin names and pin references.

- `process_metrics.py`  
  Processes raw run outputs into aggregate metrics.

#### `benchmark/expert_validation/`

Scripts and data for expert validation of assertion-based evaluation.

- `compute_human_agreement_metrics.py`  
  Computes human agreement metrics.

- `curve.py`  
  Generates threshold or agreement curves.

- `fill_final_decision.py`  
  Fills or post-processes final human decisions.

- `kappa_vs_threshold.pdf`  
  Visualization of agreement metrics across thresholds.

- `patch_apr.py`  
  Utility script for patching assertion pass rate records.

- `sampling.py`  
  Samples validation examples.

- `validation_results.csv`  
  Human validation results.

- `validation_sample/`  
  Sampled cases used for expert validation.

#### `benchmark/ground_truth_assertion/`

Ground-truth functional assertion files for each benchmark design.

The benchmark contains 20 designs across three tiers:

- Tier 1: `T1-1` to `T1-4`
- Tier 2: `T2-1` to `T2-10`
- Tier 3: `T3-1` to `T3-6`

Each file follows the naming pattern:

```text
{design_id}_assertion.json
```

For example:

```text
T2-3_assertion.json
```

#### `benchmark/reports/`

Aggregated reports and processed experiment summaries.

- `main_results.csv`  
  Main result table.

- `assertion_task_details.json`  
  Per-task assertion metadata.

- `hallucination_report.md`  
  Markdown hallucination analysis report.

- `hallucination_model_report.csv`  
  Hallucination statistics grouped by model.

- `hallucination_run_report.csv`  
  Hallucination statistics grouped by run.

- `hallucination_task_report.csv`  
  Hallucination statistics grouped by task.

- `baseline/`, `erc_only/`, `full_system/`, `tcs_only/`  
  Processed reports for different experiment settings.

#### `benchmark/results/`

Raw or intermediate experiment outputs.

- `baseline/`  
  Results from direct baseline prompting.

- `full_system/`  
  Results from the full TopoScope system.

- `ablation/`  
  Results from ablation settings.

#### `benchmark/runners/`

Experiment runner scripts.

- `run_all_task_full.py`  
  Runs the full system over all benchmark tasks.

- `run_all_task_baseline.py`  
  Runs the baseline over all benchmark tasks.

- `run_all_task_erc.py`  
  Runs the ERC-only ablation over all benchmark tasks.

- `run_all_task_tcs.py`  
  Runs the TCS-only ablation over all benchmark tasks.

- `run_full_system.py`  
  Runs the full system on a selected task or case.

- `run_baseline.py`  
  Runs the baseline on selected tasks.

- `run_erc_only.py`  
  Runs the ERC-only setting on selected tasks.

- `run_tcs_only.py`  
  Runs the TCS-only setting on selected tasks.

- `run_erc_retry_probe.py`  
  Probes ERC retry behavior.

- `llm_clients/`  
  LLM client implementations for different providers.

#### `benchmark/verification/`

- `assertion_enums.txt`  
  Enumeration of supported functional assertion types.

### `datasheets/`

- `datasheets_urls.txt`  
  Datasheet URL list used for component data construction.

### `prompts/`

Prompt templates and design knowledge used by the generation system.

- `base_design_knowledge.md`  
  General PCB design knowledge.

- `baseline_prompt.md`  
  Prompt used by the direct baseline.

- `naming_rules_prompt.md`  
  Naming conventions for modules, nets, components, and pins.

  Prompt description for the TopoScope method.

  Design knowledge used during macro-level planning.

- `phase1_base_design_knowledge.md`

Core graph construction and action utilities.

- `erc_verification.py`  
  ERC verification utilities.

- `extract_state.py`  
  Extracts graph state for prompting and evaluation.

- `graph_action.py`  
  Defines graph actions used by the agent.

## Quick Start

### 1. Create the Conda environment

```bash
conda create -n TopoScope python=3.11
conda activate TopoScope
```

### 2. Install dependencies

```bash
pip install -r requirements.txt
```

### 3. Configure LLM clients

Go to the benchmark directory:

```bash
cd benchmark
```

Edit:

```text
configs/llm_clients.json
```

Configure the following fields for the provider you want to use:

```json
{
  "base_url": "YOUR_API_BASE_URL",
  "api_key_env": "YOUR_API_KEY_ENV_NAME",
  "model": "YOUR_MODEL_NAME"
}
```

The `api_key_env` field should point to an environment variable that stores your API key.

For example:

```bash
export OPENAI_API_KEY="your_api_key_here"
```

The configuration file may contain providers such as:

- `qwen`
- `openai`
- `deepseek`
- `gemini`
- `glm`
- `kimi`

Use the provider name defined in `llm_clients.json` when launching experiments.

## Running Experiments

Enter the runner directory:

```bash
cd benchmark/runners
```

### Run the full system on all benchmark tasks

```bash
python run_all_task_full.py <provider>
```

Example:

```bash
python run_all_task_full.py openai
```

or:

```bash
python run_all_task_full.py qwen
```

### Run the baseline on all benchmark tasks

```bash
python run_all_task_baseline.py <provider>
```

Example:

```bash
python run_all_task_baseline.py deepseek
```

### Run the ERC-only ablation on all benchmark tasks

```bash
python run_all_task_erc.py <provider>
```

Example:

```bash
python run_all_task_erc.py glm
```

### Run the TCS-only ablation on all benchmark tasks

```bash
python run_all_task_tcs.py <provider>
```

Example:

```bash
python run_all_task_tcs.py kimi
```

## Running a Single Setting

Single-setting scripts support explicit command-line options. For the full-system runner, the usage is:

```text
usage: run_full_system.py [-h] [--provider PROVIDER] [--config CONFIG] [--cases CASES]
                          [--results-root RESULTS_ROOT] [--case-index CASE_INDEX]
                          [--design-id DESIGN_ID] [--run-id RUN_ID] [--list-providers]
                          [case]
```

### List available providers

```bash
python run_full_system.py --list-providers
```

### Run one design by design ID

```bash
python run_full_system.py --provider <provider> --design-id <design_id>
```

Example:

```bash
python run_full_system.py --provider qwen --design-id T2-3
```

### Run one design by case index

```bash
python run_full_system.py --provider <provider> --case-index <case_index>
```

Example:

```bash
python run_full_system.py --provider openai --case-index 0
```

### Specify a run ID

Use `--run-id` to distinguish repeated runs of the same design.

```bash
python run_full_system.py --provider <provider> --design-id <design_id> --run-id <run_id>
```

Example:

```bash
python run_full_system.py --provider deepseek --design-id T3-2 --run-id 1
```

### Use a custom config file

By default, the runner reads the standard LLM client configuration. To use another config file:

```bash
python run_full_system.py --provider <provider> --config ../configs/llm_clients.json --design-id <design_id>
```

Example:

```bash
python run_full_system.py --provider gemini --config ../configs/llm_clients.json --design-id T1-1
```

### Use a custom benchmark cases file

```bash
python run_full_system.py --provider <provider> --cases ../cases/benchmark_cases.json --design-id <design_id>
```

Example:

```bash
python run_full_system.py --provider glm --cases ../cases/benchmark_cases.json --design-id T2-6
```

### Use a custom result directory

```bash
python run_full_system.py --provider <provider> --results-root ../results/full_system --design-id <design_id>
```

Example:

```bash
python run_full_system.py --provider kimi --results-root ../results/full_system --design-id T3-5
```

### Positional case argument

The runner also accepts an optional positional `case` argument. This can be used when the script supports direct case selection by positional value.

```bash
python run_full_system.py <case> --provider <provider>
```

Example:

```bash
python run_full_system.py T2-3 --provider qwen
```

### Other single-setting runners

The same style can be used for the other single-setting scripts when their arguments are aligned with `run_full_system.py`:

```bash
python run_baseline.py --provider <provider> --design-id <design_id> --run-id <run_id>
python run_erc_only.py --provider <provider> --design-id <design_id> --run-id <run_id>
python run_tcs_only.py --provider <provider> --design-id <design_id> --run-id <run_id>
```

Examples:

```bash
python run_baseline.py --provider qwen --design-id T2-3 --run-id 1
python run_erc_only.py --provider qwen --design-id T2-3 --run-id 1
python run_tcs_only.py --provider qwen --design-id T2-3 --run-id 1
```

## Evaluation

The evaluation scripts are located in:

```text
benchmark/eval/
```

The main evaluation entry point is:

```bash
python eval/evaluate.py
```

Depending on the experiment output directory, you may need to adjust the input path or configuration inside the evaluation script.

The evaluation pipeline checks generated designs using:

- functional assertions
- connection recall and precision
- ERC-related checks
- pass/fail criteria
- hallucination diagnostics

Processed reports are saved under:

```text
benchmark/reports/
```

Raw experiment outputs are saved under:

```text
benchmark/results/
```

## Benchmark

The benchmark contains 20 PCB schematic design tasks across three complexity tiers:

| Tier | Number of Designs | Description |
|------|-------------------|-------------|
| Tier 1 | 4 | Single-module basic designs |
| Tier 2 | 10 | Multi-module collaborative designs |
| Tier 3 | 6 | System-level complex designs |

The tasks cover six application domains:

| Type | Domain |
|------|--------|
| PM | Power Management |
| SEN | Sensing and Data Acquisition |
| COM | Communication Interface |
| DRV | Motor and Actuator Drive |
| AUD | Audio Processing |
| LED | LED and Display Driver |

Ground-truth assertions are stored in:

```text
benchmark/ground_truth_assertion/
```

## Output Format

Generated designs are evaluated as connection sets. A typical output contains:

```json
{
  "components": [
    {
      "refdes": "U1",
      "part_number": "TPS54331"
    }
  ],
  "nets": [
    {
      "name": "VIN",
      "pins": ["U1.VIN", "C1.1"]
    }
  ]
}
```

Each net defines a set of electrically connected pins.
